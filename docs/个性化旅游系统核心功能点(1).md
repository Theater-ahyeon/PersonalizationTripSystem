# 个性化旅游系统核心功能点（C++ 版本）

## 1. 项目定位

本系统面向景区、校园或园区等封闭区域，采用 C++ 实现个性化旅游系统。系统以手写数据结构和算法为核心，不依赖数据库完成主要功能，通过 JSON 和二进制文件实现数据持久化。

## 2. 核心流程

系统整体流程与当前设计图保持一致：

1. 系统启动
2. `DataManager::load()` 从 JSON/二进制文件加载数据
3. 进入主菜单 CLI
4. 用户选择功能模块
5. 模块执行完成后返回主菜单
6. 用户退出时执行 `DataManager::save()`
7. 系统结束

## 3. P0 核心功能

### 3.1 景点推荐

目标：

- 根据评分、热度和偏好标签输出 Top-K 景点

实现要点：

- 数据结构：HashMap + MinHeap
- 算法：Top-K 堆排序
- 复杂度：`O(N log K)`

验收点：

- 能输出前 10 个推荐景点
- 用户点击后热度可更新并持久化

### 3.2 路径规划

目标：

- 输入起点、终点和交通方式，输出最优路线

实现要点：

- 数据结构：Graph 邻接表 + MinHeap
- 算法：A* 或 Dijkstra
- 扩展：多点路线可用 TSP 状态压缩 DP

验收点：

- 支持步行和骑行
- 输出路径节点序列、总距离和预估时间

### 3.3 场所搜索

目标：

- 支持景点、设施和餐厅名称搜索

实现要点：

- 数据结构：Trie + HashMap
- 算法：Trie 前缀补全 + KMP 字符串匹配
- 排序：按距离、评分或热度输出

验收点：

- 输入前缀时可返回候选词
- 输入完整关键词时可返回去重排序结果

### 3.4 旅游日记

目标：

- 支持日记撰写、浏览、搜索和压缩存储

实现要点：

- 数据结构：HashMap + MinHeap
- 算法：Huffman 编码/解码 + KMP 搜索
- 存储：正文存 `.bin`，元数据和编码表存 `.json`

验收点：

- 可新增、读取和搜索日记
- 可展示压缩前后体积差异

### 3.5 美食推荐

目标：

- 根据当前位置推荐附近餐厅，并支持菜系或名称筛选

实现要点：

- 数据结构：HashMap + MinHeap
- 算法：Top-K + KMP
- 排序维度：评分、热度、距离

验收点：

- 可输出附近 Top-K 餐厅
- 支持关键词筛选

## 4. P1 增强功能

### 4.1 多目标路径规划

- 适合“打卡多个景点再回到起点”的场景
- 算法：状态压缩 DP
- 约束：点数不宜过大

### 4.2 室内导航

- 支持楼层、楼梯、电梯和房间建模
- 本质上仍是图最短路问题

### 4.3 用户偏好画像

- 记录用户浏览、点击和收藏行为
- 动态影响推荐得分

## 5. 核心数据结构

### 5.1 Graph

- 作用：建模景点与道路关系
- 典型操作：`addEdge`、`getNeighbors`

### 5.2 MinHeap

- 作用：Top-K 与 Huffman 共用优先队列
- 典型操作：`push`、`pop`、`top`

### 5.3 Trie

- 作用：名称前缀搜索与补全

### 5.4 HashMap

- 作用：ID 查询、频率统计、结果去重

## 6. 核心算法汇总

| 算法 | 应用场景 | 复杂度 |
|------|----------|--------|
| Top-K | 景点推荐、美食推荐 | `O(N log K)` |
| A* / Dijkstra | 路径规划 | `O((V+E) log V)` |
| Trie | 前缀补全 | `O(M)` |
| KMP | 文本匹配 | `O(N + M)` |
| Huffman | 日记压缩 | `O(N log N)` |
| TSP-DP | 多点路径规划 | `O(2^N * N^2)` |

## 7. 数据规模建议

为了满足课程展示需求，建议准备至少以下规模的数据：

- 景点或目的地：200+
- 建筑或内部节点：20+
- 道路边：200+
- 设施：50+
- 用户：10+
