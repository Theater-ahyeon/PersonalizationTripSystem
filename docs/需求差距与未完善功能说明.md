# 需求差距与未完善功能说明

## 1. 文档目的

本文用于说明“课程需求”和“当前项目功能”之间的差距。当前项目已经具备较完整的演示闭环，但仍有一些功能属于演示版、数据规模达标但质量不足、前端界面和真实工程能力仍需继续优化。本文不用于夸大完成度，而是明确后续还需要补齐的内容，便于答辩说明和继续开发。

## 2. 当前项目概况

当前系统包含探索推荐、路线规划、附近设施查询、旅游日记、美食推荐五个主要页面。

当前数据规模如下：

| 数据项 | 当前数量 | 说明 |
| --- | ---: | --- |
| 景区/校园目的地 | 200 | 数量达到课程要求；已替换掉无意义 `????` 占位，当前为真实景区/校园名称 |
| 绑定内部路网的目的地 | 24 | 主要为颐和园内部可参与路线规划的景点/建筑 |
| OSM 路网节点 | 228 | 当前为颐和园内部数据包 |
| 有向道路边 | 526 | 达到 200 条以上要求 |
| 服务设施 | 60 | 达到 50 个以上要求 |
| 服务设施类别 | 12 | 达到 10 类以上要求 |
| 餐饮数据 | 50 | 用于美食推荐演示 |
| 系统用户 | 10 | 达到课程要求 |
| 旅游日记 | 12 | 可演示浏览、检索、评分、压缩率 |
| 区域数据包 | 4 | 只有 `summer_palace` 为已激活，其余为待接入/模板 |

## 3. 需求对照与未完善项

| 课程需求 | 当前实现情况 | 还没有实现好的地方 |
| --- | --- | --- |
| 景区和校园数量至少 200 个 | `spots.json` 已有 200 个目的地，包含 140 个景区/博物馆/古镇/自然地标和 60 个校园 | 已修复无意义占位名称；但除颐和园内部数据外，多数目的地仍是目录级数据，真实图片、真实坐标、真实简介、真实评价和热度还不够完善 |
| 景区/校园内部建筑物不少于 20 个 | 颐和园数据包中约 24 个目的地绑定了内部节点 | 只有颐和园数据包较完整，其他景区和校园没有独立内部建筑与道路图 |
| 服务设施不少于 50 个、类别不少于 10 种 | 已有 60 个设施和 12 类设施 | 设施数据主要围绕颐和园，缺少全国不同景区/校园的数据；部分设施名称和属性仍偏生成式 |
| 建立内部道路图，边数不少于 200 条 | 颐和园路网有 228 节点、526 有向边 | 全国和校园数据包还没有真实路网；地图底图和本地路网不是完整的全国导航系统 |
| 旅游推荐，按热度、评价、兴趣 Top-10 | 前端已用 Top-K 最小堆、LSH 候选、评分/热度/兴趣权重 | 推荐解释还偏简单；用户画像维度较少；动态数据变化只在前端演示，没有持久化更新 |
| 目的地名称、类别、关键字查询 | 探索页已支持关键词查询和排序 | 查询仍是前端内存检索，没有后端索引；大规模数据下需要进一步做 Trie/倒排索引/分页 |
| 单目标最短路径 | 路线页支持 Dijkstra、距离/时间/拥挤度/交通工具策略 | 当前可运行路线只覆盖颐和园数据包，不支持跨城市、跨景区、校园真实路网 |
| 多目标途经并返回起点 | 已支持 TSP-DP 演示 | 节点过多时状态压缩 DP 不适合大规模真实导航，需要启发式算法优化 |
| 交通工具策略 | 支持步行/骑行和交通工具权重策略 | 景区电瓶车、校园自行车路线目前是抽象为边类型，没有真实电瓶车站点、班次、上下车逻辑 |
| 室内导航 | 已有文昌院室内节点图演示 | 只是模拟建筑内部结构，缺少真实楼层平面图、楼梯/电梯约束、多建筑室内数据 |
| 场所查询，附近范围内设施按路径距离排序 | 设施页支持 GeoHash 候选、范围过滤、图上路径距离排序 | 搜索范围和设施仍围绕颐和园；没有实现跨数据包的设施索引；设施详情较简单 |
| 旅游日记管理 | 已支持新增日记、浏览量 +1、评分、统一列表 | 新增日记只保存在当前前端内存，刷新页面会丢失；未做真实文件上传和后端持久化 |
| 日记标题精确查询 | 已有标题 HashMap 精确查询 | 当前 HashMap 在前端内存中构建，未与 C++ 控制台或后端持久化统一 |
| 日记全文检索 | 已有 KMP 全文检索 | 全文检索只适合演示，真实大规模应改为倒排索引、分词索引或全文搜索引擎 |
| 日记无损压缩 | C++ 侧已有 Huffman 编码；前端可估算压缩字节 | 前端没有真正写入 `.bin` 压缩文件；新增日记没有持久化到 C++ 数据目录 |
| AIGC 根据照片和描述生成旅游动画 | 日记页有日记草稿和动画分镜生成入口 | 目前是规则脚本生成分镜，不是真实 AIGC 图片/视频/动画模型；没有接入模型 API，也没有生成视频文件 |
| 美食推荐 | 已支持菜系过滤、模糊查询、热度/评分/距离/综合 Top-10 | 餐饮数据仍是演示数据，缺少真实餐厅、窗口、营业时间、人均价格和真实距离 |
| 图形化地图展示 | Leaflet 地图、本地路网、节点、设施标注已实现 | 在线瓦片受网络影响；真实建筑轮廓、设施细节和全国地图数据仍不完整 |

## 4. 重点未完善问题

### 4.1 景点和校园数据还不够真实

目的地数量已经达到 200 个，并且已经将原来无意义的 `????` 占位数据替换为真实景区、博物馆、古镇、自然地标和高校名称。当前仍需要注意：这些新增目的地多数还是目录级数据。真正拥有内部路网、设施、餐饮、节点详情和路线规划能力的，仍主要是颐和园数据包。

需要继续补齐：

- 每个景区/校园的真实坐标、简介、类别、热度、评分、标签。
- 每个景区/校园内部至少 20 个建筑/景点。
- 每个区域独立的道路图、设施图层、餐饮数据。
- 更多真实图片，减少复用图片和占位图片。

### 4.2 全国可用目前只是架构和地图视野，不是完整全国导航

当前系统可以切换全国、北京、上海等地图视野，也有区域数据包 manifest。但实际可运行的路线、设施距离和多点游览算法仍基于 `summer_palace` 数据包。

后续需要：

- 为不同城市、景区、校园建立 `cpp/data/regions/{region_id}` 数据目录。
- 每个目录提供 `spots.json`、`osm_nodes.json`、`osm_edges.json`、`facilities.json`、`restaurants.json`。
- 前端选择区域后真正加载对应数据包，而不是只切换地图中心点。
- 使用 OpenStreetMap/Overpass 或合法 API 获取路网，避免抓取不合规地图瓦片。

### 4.3 AIGC 功能仍是演示入口

当前 AIGC 功能可以根据文字和用户偏好生成“日记草稿”和“动画分镜”，适合作为答辩中的扩展功能说明。但它还不是完整 AIGC 功能。

未完成内容：

- 没有识别真实上传照片中的景点。
- 没有接入文生图、图生视频或动画生成模型。
- 没有生成实际视频、动图或可下载动画文件。
- 没有保存 AIGC 生成结果到日记系统。

建议后续把它定位为“可扩展接口”，不要在答辩中声称已经实现真实动画生成。

### 4.4 日记新增和媒体上传没有持久化

前端已经支持新增日记、选择图片/视频文件、浏览量 +1 和评分，但这些更新只存在当前页面状态中。

未完成内容：

- 刷新页面后新增日记会丢失。
- 选择的图片/视频只记录文件名，没有上传、预览、存储。
- 前端新增日记没有写入 `cpp/data/diaries/index.json`。
- 前端 Huffman 压缩只是估算，没有生成真实 `.bin` 文件。

后续需要增加后端保存接口，或者提供本地导出 JSON/压缩文件的功能。

### 4.5 前端界面还需要继续打磨

当前前端已经能演示功能，但界面仍有优化空间。

主要问题：

- 功能密度较高，路线页侧栏内容偏多，用户第一次使用时容易感觉复杂。
- 地图底图依赖在线瓦片，网络受限时视觉效果会下降。
- 部分算法提示文字偏课程答辩风格，普通用户视角下不够自然。
- 日记编辑区、AIGC 区和日记浏览区可以进一步分层，减少视觉拥挤。
- 移动端虽然有响应式样式，但复杂表单和地图侧栏仍需要进一步实测优化。

### 4.6 算法与 C++/前端的一致性还可加强

项目中 C++ 侧已经有 MinHeap、HashMap、Trie、KMP、Huffman、Dijkstra、TSP 等算法。前端也补了 Top-K、GeoHash、LSH、KMP 等演示逻辑。

仍需加强：

- 前端和 C++ 的算法结果没有统一对照测试。
- 部分功能在前端更完整，C++ 控制台未同步展示，如 GeoHash 和 LSH。
- 前端新增日记没有调用 C++ Huffman 压缩逻辑。
- 推荐、路线、设施查询的测试主要是 smoke，缺少细粒度单元测试。

## 5. 建议后续完善优先级

### P0：必须优先补

1. 建立至少 1 个校园数据包，体现“景区和学校都可用”。
2. 补齐更多真实图片和真实简介，避免推荐卡片看起来像占位数据。
3. 新增日记持久化方案，至少支持导出或写回 JSON。
4. AIGC 功能改成明确的“模拟分镜/待接入模型”，避免误导。

### P1：增强答辩说服力

1. 为北京或校园区域接入一份新的 OSM 路网数据包。
2. 增加算法复杂度说明和结果对比，例如完全排序 vs Top-K 堆。
3. 增加前端和 C++ 的一致性测试。
4. 优化路线页布局，降低侧栏压迫感。

### P2：长期工程化

1. 引入后端服务或本地存储，支持用户、日记、评分、浏览量持久化。
2. 接入真实 AIGC API 或本地模型服务。
3. 扩展地图数据采集脚本，批量生成区域数据包。
4. 为大规模日记和目的地数据建立倒排索引、分页和缓存。

## 6. 当前答辩时建议表述

可以这样表述当前项目状态：

> 本项目已经实现个性化旅游系统的核心算法演示，包括 Top-K 推荐、Dijkstra 路线规划、TSP 多点游览、GeoHash 附近设施检索、KMP 日记全文检索、HashMap 标题精确查询、Huffman 压缩统计和 LSH 兴趣相似检索。数据规模达到课程要求，但真实区域数据目前主要集中在颐和园数据包。全国地图和区域数据包架构已经预留，后续需要继续接入更多真实景区和校园路网。AIGC 功能目前为分镜生成演示入口，尚未接入真实视频生成模型。

这样说比较准确，也能体现已经完成的算法价值和后续改进方向。
