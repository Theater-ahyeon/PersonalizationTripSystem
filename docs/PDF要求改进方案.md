# 基于课程 PDF 要求的项目改进方案

## 1. PDF 核心要求提炼

课程设计题目是“个性化旅游系统的设计与实现”，验收重点不是数据库或普通 Web 页面，而是围绕旅游业务场景展示手写数据结构和算法：

- 旅游推荐：按热度、评价、个人兴趣生成 Top-10，不经过完全排序，支持名称、类别、关键字查询。
- 路线规划：支持单目标最短路径、多目标途经后返回起点；支持最短距离、最短时间、交通工具策略、拥挤度；需要地图和路径展示。
- 场所查询：按类别和关键字查找附近设施，并按图上路径距离排序，不能只用直线距离。
- 日记管理与交流：支持日记浏览、评分、热度、兴趣推荐、目的地查询、标题精确查询、全文检索、无损压缩。
- 美食推荐：选中景点后，按热度、评价、距离 Top-10 推荐，支持菜系过滤和模糊查询。
- 数据规模：至少 20 个建筑/景点、50 个服务设施且不少于 10 类、200 条以上道路边、10 个用户；建议使用真实地图数据。
- 工程要求：不使用数据库完成核心功能；核心算法必须自己实现；需要文档、测试、演示证据和 AI 协作过程说明。

## 2. 当前项目状态

当前项目已经具备较好的验收基础：

- 数据：228 个 OSM 节点、526 条有向道路边、24 个景点/建筑、60 个设施、12 类设施、50 条餐饮、10 个用户、12 条日记。
- 算法主体：C++ 侧已有 `HashMap`、`MinHeap`、`Trie`、Dijkstra/A*、TSP-DP、KMP、Huffman、Top-K 推荐。
- 前端演示：已有推荐、路线、设施、日记、美食、验收台六个页面，支持地图绘制和 smoke 验证。

主要不足与本轮修复状态：

- 数据规模：`spots.json` 已从 24 个扩展到 200 个全国景区/校园目的地；前 24 个继续绑定颐和园内部路线节点。
- GeoHash 附近检索：设施查询已增加 GeoHash 前缀桶，先缩小候选集，再按图上最短路径距离排序。
- 路线规划：已展示最短距离、最短时间、拥挤度时间、交通工具策略。
- 室内导航：已增加文昌院室内模拟节点图，覆盖大门、电梯、楼层和房间导航。
- AIGC 动画生成：已增加日记页“动画分镜生成”演示入口，当前为脚本生成，不伪装成真实视频模型。
- 日记检索：已区分全文检索、标题精确查询和目的地查询。

## 3. 改进优先级

### P0：答辩验收证据补强

1. 在验收台增加 PDF 要求覆盖矩阵，逐项显示：状态、数据证据、算法、演示入口。
2. 在路线页增加策略选择：最短距离、最短时间、拥挤度时间、交通工具策略。
3. 在路线结果中显示策略说明、总距离、估算时间和拥挤度逻辑。
4. 在推荐、设施、日记、美食结果上补充算法标签，让老师能直接看到“核心算法”。

### P1：核心功能补强

1. 日记页增加标题精确查询入口，和全文检索区分开。
2. 设施查询继续使用图上路径距离，并在结果中标注“路径距离排序”。
3. 美食推荐显示 Top-K 证据，按距离、评分、热度综合排序。
4. C++ smoke 和 Web smoke 增加 PDF 覆盖检查。

### P2：高级要求说明与可选实现

1. 室内导航：用“文昌院室内模拟图”做三层节点图，大门、电梯、展厅/房间最短路径。
2. AIGC 动画生成：作为课程创新点可做前端 mock 流程，明确当前是演示入口，不冒充真实模型。
3. 增加算法复杂度表和性能对比表。

## 4. 本轮实施范围

本轮先实施 P0：

- 新增验收矩阵数据结构和渲染。
- 新增路线策略控件与加权路径计算。
- 改造路线摘要，让演示中能说清“距离/时间/拥挤度/交通工具”。
- 更新 smoke 检查，确保新增入口不丢失。

## 5. 剩余风险

- 200 个景区/校园目的地已在 `spots.json` 中补齐，但其中只有前 24 个绑定了颐和园内部道路图；如果要做到全国真实路线规划，需要为每个城市或景区继续生成独立道路图数据包。
- AIGC 动画生成目前是前端分镜脚本演示入口，不是真实视频模型；答辩时应说明它展示的是输入、分镜和后续接入位置。
- 真实在线地图瓦片在受限网络环境下可能无法加载，项目仍保留本地道路、建筑和设施标注作为离线演示层。
